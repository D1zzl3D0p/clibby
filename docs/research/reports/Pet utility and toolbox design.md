# Give desktop pets useful everyday jobs

Better Pets should next become an **attention inbox with a small summoned toolbox**, supported by optional status cards. These three features cover most useful capabilities found in desktop pets and Mac utility launchers without turning the project into a second operating system. The first practical use should be a real work event that produces a readable card with **Open source** and **Acknowledge**, rather than more wandering animations. For the body, add stable head/card/effect anchors and a small semantic gesture layer; give the werewolf target-driven arm and hand control, while keeping Mallow's arms optional. Existing session state, local IPC and procedural locomotion provide much of the foundation, but genuine tool adapters and interactive cards are still proposals. Ratings below are subjective usefulness judgments for this user's coding/chat workflow; neither the comparison nor native app inspection establishes battery performance.

## Actionable work signals offer more value than pet chores

The closest useful precedents connect a companion to work already happening. AgentPet collects agent states, elapsed time and projects, while UniPet accepts normalized lifecycle events through adapters. PeonPing demonstrates that completion, input requests and failures need suppression, deduplication and a route back to the source. These projects support treating the pet as a friendly front door to an existing workflow. They do not establish that every chat application exposes the necessary events. ([AgentPet](https://github.com/ntd4996/agentpet), [UniPet](https://github.com/ydyangdan/UniPet), [PeonPing](https://github.com/PeonPing/peon-ping/blob/main/README.md))

Scores mean **5 = frequent practical value**, **3 = useful in selected workflows**, and **1 = mainly novelty or interference**. They rate what Better Pets could borrow, not the quality or popularity of each project. Features come from primary project documentation; these applications were not installed and benchmarked for this comparison.

Mac launchers contribute the interaction structure that pets often lack. Raycast attaches contextual actions to items and lets one in-progress toast change into success or failure. Alfred composes triggers, data and actions, including actions appropriate to text, files or links. SwiftBar combines glanceable state with menus and supports temporary event-created items. Hammerspoon supplies a searchable chooser and focus restoration. ([Raycast actions](https://developers.raycast.com/api-reference/user-interface/action-panel), [Raycast toast](https://developers.raycast.com/api-reference/feedback/toast), [Alfred workflows](https://www.alfredapp.com/help/workflows/), [Alfred Universal Actions](https://www.alfredapp.com/help/features/universal-actions/), [SwiftBar](https://github.com/swiftbar/SwiftBar), [Hammerspoon chooser](https://www.hammerspoon.org/docs/hs.chooser.html))

Their most useful subset is modest: a contextual primary action, a searchable panel, and feedback that updates an existing item. Raycast's action/status pattern and SwiftBar's event-fed status/menu pattern score **5/5** for transfer; Alfred's typed actions and Hammerspoon's chooser score **4/5**. Recreating their extension stores, workflow editors or desktop automation engines would add much more scope than everyday value.

An initial “Open Vorsaint” action would be cheaper than rebuilding its tools; deeper actions depend on a supported command or deep-link interface. ## Three shared surfaces cover notifications, tools and displays

The recommended product shape collates many apparently separate requests into three families. The same item can begin as a brief above-head card, remain in an inbox, and expose an action in the toolbox. Animation communicates significance; a conventional panel provides readable text and controls.

| Family | Usefulness / 5 | Relative effort | Proposed battery fit | Features consolidated |
|---|---:|---|---|---|
| **Attention inbox** | 5 | Medium: provider adapter and interactive presentation | Strong with pushed events, expiry deadlines and brief cues | Response ready, input/approval required, task failure, build result, reminder due |
| **Summoned toolbox** | 4 | Medium for a curated action registry | Strong when opened and populated on demand | Open chat/project/app, start timer, capture note, run an existing user-selected tool |
| **Status cards** | 4 | Low–medium when reusing the card model | Strong for deadline-based timers and visible-only updates | Focus countdown, waiting count, selected job progress, tool result |
| Rich props and direct manipulation | 3 | Medium–high | Good when interaction starts the work | Hold a sign, present an item, accept a dropped file/link |

Battery fit here describes scheduling choices, **not measured energy use**. Preserve the resident's one quiet deadline timer; a reminder needs a wakeup at its deadline, not a check on every animation frame. Providers should push state changes. Progress should use real provider values and coarse updates while visible, rather than invented percentages or continuous shell polling.

Use one shared **CardAction model**: stable card and source identity, title/plain text, status, unread/acknowledgment state, timestamp/lifetime, optional progress or deadline, and registered action descriptors. Notification cards and toolbox entries should share the action registry. Keep provider data, action execution and presentation policy separate. A provider supplies meaning; the shell chooses bubble, badge, panel, optional sound or native notice. An incoming event must not become an arbitrary shell command.

The existing session core already accepts `working`, `needs_input`, `completed` and `failed`, with identifiers, increasing sequences, TTL, arbitration and acknowledgment. Its checked-in producer is simulated; no real coding-tool adapter is implemented, and live socket acceptance remains open in this sandbox. The current status label is plain text, input-transparent and positioned from fixed offsets. It is not yet an interactive speech/card surface. Build on that core rather than creating a competing notification store. ([Session API](../../api/session-v1.md), [Handoff](../../handoff.md), [Status label](../../../qt/resident/status_label.cpp))

## Stable anchors and hand goals let either body communicate

Start with anatomy-independent fixtures: an **attention anchor above the head**, an effect anchor, a card-facing/look target and optional left/right grip sockets. Project a 3D anchor into desktop coordinates while rendering text in ordinary 2D UI. Keep bubbles within the current screen, away from the pointer and clear of the pet's silhouette. Expanded text and buttons belong in a keyboard-accessible panel. A pixel sign can be a prop, but its text should not be baked into a tiny texture.

Mallow should first communicate through its head, eyes, ears, tail and a small body gesture. Short mitten arms can be added once their silhouette reads at actual desktop size; every useful feature needs a fallback when a character has no arms. The werewolf already has upper-arm, forearm and hand joints, so it is the natural first hand-IK implementation. Current arm followers react to motion but do not yet expose reach, point, wave or hold targets. ([Mallow anatomy](../../../characters/soft-creature/manifest.json), [Werewolf rig](../../../characters/werewolf-3d/rig.json), [3D pose interface](../../../qt/characters3d/pose.h))

Define semantic capabilities rather than one compulsory skeleton: `lookAt`, `reachLeft`, `reachRight`, `point`, `wave`, `hold`, optional expression, and `effectAnchor`. Arm definitions need shoulder–elbow–hand chains, measured segment lengths, limits, bend/pole preferences and grip offsets. Their solver should support unequal lengths independently of the current Mallow leg-planner restriction. Give the visible-side arm preference for wave/point; two-hand signs can request a stop before grasping. A gesture should provide goals and a bounded envelope for procedural motion, not introduce authored frame sheets.

The useful first vocabulary is looking at the card, a small one-hand wave, pointing, presenting an item, nodding, a brief success response and lowered-head failure. Compose these with walking while **ground contacts retain authority**. Holding a prop must not overwrite leg IK. Preview contact and grip markers through reversal, dragging, pause and screen clipping before adding throwing, jumping, climbing or lip-sync.

Attention should rise once, then settle: glance or ear cue, a short wave/effect, then a static unread indicator. A restrained badge or small mark is sufficient; continuous waving, pulsing or repeated celebratory effects would make useful signals difficult to ignore when the user intentionally postpones them.

## One real event round trip should prove the next feature

The first implementation slice should connect **one real producer the user already uses** to an above-head card and small inbox. The adapter emits working, needs-input, response-ready or failed events through the existing boundary. The pet performs one short gesture; the card offers **Open source** and **Acknowledge**, and an unread indicator survives after the gesture finishes. Opening and acknowledging remain separate actions: returning to a task does not prove that its pending request was resolved.

Claude Code is a documented candidate because its hooks expose prompt submission, permission requests, notifications, response stops and failures. Its semantics need care: `Stop` identifies a finished response and can coexist with background work; permission requests have a direct hook, and completion notifications are not uniformly successful. This is evidence for a possible adapter, not evidence that the user runs it. A wrapper around a real build is a dependable fallback if no supported chat event source is available. ([Official hook reference](https://code.claude.com/docs/en/hooks))

“Chat needs refreshing” needs an explicit source-defined event. Lack of activity, transport failure or TTL expiry means unknown/offline, not success and not permission to reload a chat. The assistant's available chat tools do not establish a supported event API for the resident application. Avoid private-chat scraping or inferred status classification; use clear labels such as “Response ready” when that is what the source actually reports.

Acceptance should cover a real event round trip, accurate labels, user-initiated source return, acknowledgment, duplicate suppression, expiry/offline handling, and hide/pause/sleep behavior. Native desktop checks must separately establish click/focus regions, edge placement, 3D presentation and wakeups/resource cost. The current software-verified werewolf foundation does not close those checks. After that slice works, the toolbox can add pinned source/project actions and one timer using the same card/action machinery. This order makes the pet useful before a large collection of tools or body fixtures creates maintenance work.
